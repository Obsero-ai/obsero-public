Obsero ingestion › Get started

Stream CDN request logs to Obsero

Every HTTP request hitting your CDN becomes one POST to Obsero, so AI agent traffic can be classified on the request headers it actually sent.

Two working end-to-end implementations — AWS CloudFront and Google Cloud — plus a demo site and a traffic harness for each. This is a starting point, not a product. Fork it, keep the parts that match your stack, throw away the rest.

Quickstart →

One command, three steps: deploy a mock site, create the pipeline, tear it down.

The contract →

The URL and the payload. The only thing you have to get right.

AWS →

CloudFront → Firehose → Lambda adapter. One real decision to make.

Google Cloud →

LB request logs → Pub/Sub → Cloud Run adapter. Named headers on the cheap path.

#The shape of it

Obsero cares about exactly two things: the URL you POST to, and the payload. Everything else — which cloud, which log source, which language, whether you batch, whether you use Terraform at all — is your call.

That is the whole integration. Read the contract in full →

#Which one do I want?

Your setupStart hereWhy
CloudFront in front of anythingAWSTwo log sources: cheap (User-Agent only) or full headers for ~$11/mo.
Google Cloud load balancer + Cloud CDNGCPFull headers on the cheap path — no trade to make.
A plain GCS bucket behind Cloud CDNGCP, caveat firstBackend buckets emit no request logs at all. Your origin has to be a backend service.
Cloudflare, Fastly, Akamai, a bare originnone of themImport sendEvent and call it from wherever you already see requests. That is the entire integration.

#What's in the repo

obsero.mjs      the contract: build an event, validate it, POST it
setup.sh        the interactive installer
destroy.sh      teardown, plus a sweep for resources Terraform lost track of
aws/            CloudFront -> Firehose -> Lambda adapter -> Obsero
gcp/            LB request logs -> Pub/Sub -> Cloud Run adapter -> Obsero
docs/           this site

Each cloud directory has the same three parts:

ingestion/      the Terraform module you would actually ship
site/           a demo site to point it at, so you can see traffic flow
test/           a traffic harness: 19 client personas, then score what arrived

Both ingestion/ modules deploy on their own. site/ and test/ exist to prove the thing works and are the first things to delete once it does.

#If you work with a coding agent

There are AGENTS.md files at the repo root and in each cloud directory. They carry the contract, the setup order, the failure modes that look like bugs but are not, and the handful of things in the Terraform that must not be “cleaned up” because they fail silently when removed. Point your agent at them before it touches anything.
